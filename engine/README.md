# HOLO ENGINE — движок 3D-голограмм коммунальных объектов

Движок превращает **любую GLB-модель** (техника, оборудование, здания, станции) в
самодостаточную **интерактивную голограмму** в едином оффлайн-HTML-файле, который
можно открыть двойным кликом или встроить на сайт через `<iframe>`. Визуальный
эталон — файл `Суперкар (оффлайн).html`; движок обобщает его в конфигурируемый
рантайм + сборочный пайплайн.

---

## 1. Что это даёт

- **Рентген-голограмма**: каркас модели (извлечение рёбер), скан-линия, bloom,
  отражение, полупрозрачная оболочка, анимация «сборки», авто-вращение.
- **Анимация потоков среды** (`flows` в конфиге): светящиеся стрелки бегут по
  контурам вдоль направляющих труб (теплоноситель/пар/газ/ХВС) — «как работает
  объект». Кнопка «⇢ Потоки» + легенда цветов. См. §6.6.
- **Два режима** (выбираются автоматически):
  - **`structured`** — модель с материалами/узлами разбивается на именованные
    системы → клик по детали, список систем, **разборка на узлы** (explode),
    подписи-выноски. *(пример: `aAIgtiiP.glb` → 5 систем авто.)*
  - **`whole`** — единый слитый меш (AI-генерация TRELLIS, фотограмметрия, скан)
    показывается цельной голограммой: вращение, масштаб, плотность каркаса.
    *(пример: `Илосос.glb` — 1 меш, 527k вершин.)*
- **Оффлайн**: внутрь файла зашиты Three.js, загрузчики, Draco-декодер, шрифты и
  сама модель (gzip+base64). Интернет не нужен.

---

## 2. Структура

```
engine/
  build.js               # сборочный пайплайн (Node, без зависимостей)
  serve.js               # локальный статический сервер для предпросмотра
  runtime.json           # снапшот рантайма (three/шрифты/draco) — см. --snapshot
  src/
    viewer.html          # шаблон UI + каркас класса + init; токены "__ENGINE_CONFIG__"
                         #   и "/* __ENGINE_MODULES__ */" (сюда встают модули)
    modules/             # методы класса по секциям, склейка по алфавиту имён:
      10-generators.js   #   процедурные генераторы (МКД/котельная/ТЭЦ/ЦТП + declarative)
      20-model.js        #   режимы, очистка сканов (weld/smooth)
      30-render.js       #   контурный пасс, grade, edges/shell/нормализация
      40-markers.js      #   нумерованные выноски + калибровка
      50-plans.js        #   план этажа + разрез фасада
      60-flows.js        #   анимация потоков среды
      70-scene.js        #   сцена, камера, указатель, animate, действия
      80-shaders.js      #   все шейдеры (line/bold/inner/shell)
      90-ui.js           #   renderVals (правая панель, кнопки, счётчики)
  tools/
    gen-vns.js           # генератор декларативного конфига (метры → доли bbox)
  configs/               # по конфигу на объект (ilosos, supercar, mkd, mkd-121,
                         #   boiler, power, ctp, vns)
  out/                   # собранные демо
```

Готовые результаты:
- `Илосос (голограмма).html` — демо коммунальной техники (whole-режим).
- `engine/out/Суперкар (через движок).html` — проверка structured-режима через движок.

## 3. Как собрать голограмму

```bash
cd engine
node build.js --config configs/ilosos.json --model "../Илосос.glb" \
              --out "../Илосос (голограмма).html"
```

Аргументы:
- `--config`  — JSON-конфиг объекта (см. ниже).
- `--model`   — путь к GLB.
- `--out`     — путь выходного HTML (по умолчанию рядом с моделью).
- `--check`   — только проверить конфиг (валидация без сборки).
- `--runtime` — явный бандл-источник рантайма (перекрывает снапшот).

### Снапшот рантайма (`engine/runtime.json`)

Рантайм (Three.js r134, аддоны, Draco-wasm, шрифты, распаковщик, шапка шаблона)
извлекается из референс-бандла **один раз**:

```bash
node build.js --snapshot        # Суперкар (оффлайн).html → engine/runtime.json (~1МБ)
```

Дальше все сборки читают `runtime.json` и **не требуют** 15-МБ референс-файла.
Проверено: выход из снапшота байт-в-байт совпадает с выходом из референса.
Явный `--runtime <бандл>` заставляет читать референс напрямую (и им же можно
пересоздать снапшот: `node build.js --snapshot <путь>`).

### Валидация конфига

При каждой сборке (или отдельно через `--check`) конфиг проверяется:
индексы `matRules.part`/`defaultPart` в диапазоне систем, ключи `hotParts`/
`innerPartKey`/`explodeDirs` существуют в `parts`, у `markers` корректные `at`
(предупреждение при выходе за bbox), у `flows` ≥2 точек и валидные цвета,
известный `building.type`, а каждый примитив `geometry` — правильной формы
(число аргументов, mat-строка, ось `cyl`, `repeat ≥ 1`, рекурсивно в группы).
Ошибки валят сборку (exit 1), предупреждения — нет.

Предпросмотр:
```bash
node serve.js          # http://localhost:8777/  (по умолчанию открывает Илосос)
# или любой файл:  http://localhost:8777/engine/out/<имя>.html
```

## 4. Формат конфига

```jsonc
{
  "title": "Илосос",                       // крупный заголовок
  "category": "ЖКХ · КОММУНАЛЬНАЯ ТЕХНИКА", // моно-метка сверху
  "subtitle": "…",                          // описание под заголовком
  "accent": "cyan",                         // cyan | amber | green | violet
  "mode": "auto",                           // auto | structured | whole
  "density": "med",                         // low | med | high (плотность каркаса)

  // --- только для structured ---
  "hotParts": ["engine", "wheels"],         // системы, светящиеся КРАСНЫМ (рентген внутренностей)
  "hotColor": [1.0, 0.10, 0.05],            // цвет «горячих» систем
  "hotIntensity": 1.0,                       // яркость красного
  "hotAngle": 32,                            // угол рёбер для горячих систем (грубее → чистые кольца, не «диск»)
  "shellOpacity": 0.2,                       // прозрачность кузова-оболочки (ниже → внутренности видны ярче)
  "bloom": { "strength": 0.5, "radius": 0.7, "threshold": 0.0 }, // свечение
  "grade": { "exposure": 1.06, "contrast": 1.06, "saturation": 1.12 }, // финальный ACES tone-map + цветокоррекция
  "exclude": [{ "name": "object_4" }, { "mat": "material.011" }], // выкинуть мусорные меши
  "parts": [                                // список систем (порядок = номера)
    { "key": "body", "name": "Кузов", "tag": "ОБОЛОЧКА", "desc": "…" }
  ],
  "matRules": [                             // материал → индекс системы (по порядку, первый матч)
    { "match": ["engine"], "part": 2 },     // substring; "^regex" для регулярки
    { "match": ["^material\\.\\d"], "part": 4 }
  ],
  "defaultPart": 0,                         // куда падает неклассифицированное
  "explodeDirs": {                          // направление разлёта в нормализованном пространстве
    "glass": [0, 2.4, 0], "wheels": [0, -2.1, 0]
  },

  // --- для whole (необязательно) ---
  "overview": { "tag": "…", "title": "…", "desc": "…" }, // карточка-обзор справа
  "counter": "ИЛОСОС · ВАКУУМНАЯ МАШИНА",

  // --- очистка «помятых» сканов (TRELLIS/фотограмметрия) ---
  "smooth": 5,          // итераций лапласова сглаживания (whole по умолч. 4; 0 = выкл)
  "smoothLambda": 0.5,  // сила сглаживания за итерацию
  "weldPrecision": 4,   // округление координат при сварке вершин (знаков после запятой)

  // --- яркость каркаса ---
  "contour": 0,         // яркость 3D-каркасных контуров (structured 1.0; whole ≈0 — заменён экранным пассом)
  "fill": 0.15,         // приглушение тонкой внутренней «заливки»-призрака (whole ≈0.15, structured 1.0)

  // --- чёткий контур по рёбрам (экранная детекция нормалей+глубины) ---
  "outline": true,         // вкл/выкл (по умолч. вкл для whole, выкл для structured)
  "outlineWidth": 1.5,     // радиус выборки рёбер, px
  "outlineIntensity": 1.7, // яркость ВНЕШНЕГО контура (силуэт + перекрытия, по глубине)
  "outlineInnerIntensity": 0.75, // яркость ВНУТРЕННИХ контуров (переломы нормалей);
                           //   по умолчанию 0.45×outlineIntensity — устройство видно,
                           //   но силуэт остаётся главным
  "outlineInnerColor": [1.0,0.62,0.18], // цвет внутренних контуров (по умолч. янтарный) —
                           //   тёплое «нутро» визуально отделяется от голубого силуэта
  "contourNormal": 1.3,    // порог перелома нормали (НИЖЕ → больше внутренних линий;
                           //   для гладких скан-мешей 1.2–1.5 проявляет устройство)
  "contourDepth": 0.005    // порог скачка глубины (силуэт и перекрытия; ниже → чувствительнее)
}
```

`mode: "auto"` сам выбирает режим: если в модели >1 материала **и** правила
`matRules` реально раскладывают её более чем в одну систему — `structured`,
иначе `whole`. Можно жёстко задать `"structured"` / `"whole"`.

### Двухцветный «рентген» (голубой кузов + красные внутренности)

Эталон-картинка X-ray авто = голубой полупрозрачный кузов + **раскалённые
красным** внутренние системы (двигатель, трансмиссия, диски колёс) + свечение.
В движке это `hotParts` — список систем, которые рендерятся красным проходом
(`uColor2`), пока остальные остаются голубыми. Чтобы красное читалось, а не
сливалось в белое под аддитивным блендингом:
- `hotAngle` грубее обычного → плотные колёса дают **чистые красные кольца**, а
  не насыщенный «диск»;
- `shellOpacity`/`contour`/`fill` приглушают голубой кузов → внутренности видны;
- `bloom` добавляет свечение, как на референсе.

**Важно:** этот вид требует модели с реальными внутренними деталями (как Суперкар,
34 материала). На едином скан-меше (Илосос, TRELLIS) внутренностей нет — красить
нечего; для техники ЖКХ так получится только с многодетальными/CAD-моделями.

### Процедурные здания (без GLB) — `source: "procedural"`

Для зданий/МКД модель не нужна — движок строит каркас из параметров. В конфиге:
`source: "procedural"` + блок `building`. Каждый элемент — тонкий бокс, поэтому
общий EdgesGeometry-конвейер даёт чистые архитектурные линии; имена материалов
маппятся в системы через `matRules`, а **инженерные стояки помечены `hot`** и
светятся цветом.

```jsonc
{
  "source": "procedural",
  "building": {
    "type": "mkd",
    "floors": 9, "floorHeight": 3.0,
    "sections": 3, "sectionWidth": 7.0, "depth": 12.0,
    "windowsPerSection": 3,
    "risers": ["water", "heat", "sewer", "electric"]  // вертикальные стояки (горячие)
  },
  "hotParts": ["systems"], "hotColor": [1.0,0.58,0.16],  // стояки — янтарём
  "shellOpacity": 0.14, "fill": 0.4, "contour": 0.45      // кузов приглушён, чтобы стояки просвечивали
}
```

Сборка без `--model`:
```bash
node build.js --config configs/mkd.json --out "../Жилой дом (МКД) (голограмма).html"
```

Демо: `Жилой дом (МКД) (голограмма).html` (~1 МБ, без модели). 9-этажный 3-секционный
дом: несущие конструкции, фасад с окнами и балконами, входные группы, кровля и
**4 инженерных стояка** (ХВС/ГВС, отопление, канализация, электрика), видимые
вертикальными янтарными линиями сквозь приглушённый голубой корпус. Сбоку — список
систем (с разборкой), таблица ТТХ и нумерованные выноски. Стены/этажность/стояки
правятся в `building`; чтобы увидеть стояки наглядно — «Разобрать» или выбрать
систему в списке.

> Для зданий разбор/выбор системы — главный учебный приём: в собранном виде стояки
> частично скрыты фасадом (аддитивная прозрачность), а explode разносит фасад,
> кровлю и стояки. Сложные/реальные здания можно и грузить как GLB (structured-режим).

#### Планировки квартир + режим «План этажа»

Генератор строит **внутренние перегородки квартир** (состав секции задаётся в коде
`buildProceduralModel`: для 121-й — 1Б, 2Б и две 3Б вокруг лестнично-лифтового узла),
комнаты помечаются (`Комната/Кухня/С/у/Прихож.`) и пишутся в `this.planRooms`.

Кнопка **«План этажа»** включает чертёжный режим: камера становится квази-ортогональной
(узкий fov сверху), один этаж изолируется по высоте (шейдерные `uPlan/uPlanY/uPlanH`
гасят остальные), оболочка/отражение/«пол» скрываются — остаётся **чистый план типовой
блок-секции** с подписями комнат. Кнопки **▲/▼** листают этажи. Демо: 121-я серия,
9 этажей, типовая секция 1Б-2Б-3Б-3Б.

Готовый файл: `Панельная 9-этажка (121 серия) (голограмма).html` (конфиг `configs/mkd-121.json`).

#### Режим «Разрез фасада» (3D-кукольный дом)

Кнопка **«Разрез фасада»** убирает переднюю стену и показывает квартиры в объёме:
шейдер отсекает фрагменты по модельной оси Z (`uCut/uCutZ`, varying `vMZ=position.z`),
оболочка/отражение скрываются, камера встаёт фронтально-сверху. Кнопки **⟨/⟩**
двигают плоскость среза вглубь/наружу. Срез — по модели, поэтому при вращении он
остаётся на «фасаде». Режимы «План этажа» и «Разрез фасада» взаимоисключающие.
9-этажный дом в разрезе плотный по своей природе (все этажи сразу) — для чистого
поэтажного чтения служит «План этажа».

#### Котельная и станции — `building.type: "boiler"`

Тот же процедурный режим строит не только жилые дома, но и **тепломеханические
объекты**. `genBoilerHouse` генерирует водогрейную БМК: здание-блок-модуль, котлы с
барабанами и горелками, газоходы и **дымовую трубу-«сэндвич»**, сетевые насосы,
деаэратор + водоподготовку, теплообменники ГВС, подающий/обратный коллекторы, щит
КИПиА и ГРУ. Добавлен helper `cyl()` (цилиндры для баков/котлов/трубы).

**Горячий контур** (котлы + дымоудаление) помечен `hotParts` и светится красным;
остальное оборудование — голубое. 7 систем в списке (с подсветкой/разборкой),
12 нумерованных выносок, таблица ТТХ, «Разрез фасада» — заглянуть внутрь блок-модуля.

```bash
node build.js --config configs/boiler.json --out "../Котельная (голограмма).html"
```

Демо: `Котельная (голограмма).html`. Параметры в `building`: `width/height/depth`,
`boilers` (число котлов), `chimneyHeight`. Так же можно описывать ТЭЦ/насосные/ЦТП —
набором примитивов (box/cyl) + `matRules`/`hotParts`.

**Электростанция (ТЭЦ)** — `building.type: "power"` (`genPowerPlant`). Главный корпус
(котлы + паровые турбины + генераторы + конденсаторы), дымовая труба, **башенные
градирни** (гиперболоид ≈ два усечённых конуса, helper `frustum()`), блочные
трансформаторы и **ОРУ** (порталы + сборные шины). Красным светится паротепловой
контур `hotParts:["boilers","turbines","exhaust"]`, голубым — генераторы/охлаждение/
электрика. 7 систем, 11 выносок, ТТХ. Демо: `Электростанция ТЭЦ (голограмма).html`
(конфиг `configs/power.json`; параметры `hallW/hallDepth/boilers/chimneyHeight/towers`).

**ЦТП (центральный тепловой пункт)** — `building.type: "ctp"` (`genCTP`). Независимая
схема присоединения квартала: **ввод теплосети** (подающий/обратный, грязевики,
задвижки, узел учёта тепла) → **пластинчатые теплообменники** (отопление + ГВС
двухступенчатые) → **распределительные коллекторы** вторичного контура → потребители;
**насосные группы**, **ХВС и подпитка** (мембранные баки), **автоматика/КИПиА**.
Красным светится тепловой контур `hotParts:["input","hx","manif"]`, голубым — насосы,
ХВС и автоматика. 7 систем, 11 выносок, ТТХ. Демо: `ЦТП (голограмма).html`
(конфиг `configs/ctp.json`; параметры `width/height/depth`).

#### Декларативная геометрия — `geometry` (объекты без кода)

Объект можно описать **целиком в конфиге** списком примитивов — движок не
трогается вовсе. Если в конфиге есть `geometry`, он имеет приоритет над
`building.type`:

```jsonc
"geometry": [
  { "box":     [16, 5, 10,   0, 2.5, 0, "shell"] },      // [sx,sy,sz, cx,cy,cz, mat]
  { "cyl":     [3.0, 4.5,   -13, 2.25, 0, "tank"] },     // [r,h, cx,cy,cz, mat, axis?]
  { "frustum": [0.25, 3.05, 0.9,  -13, 4.95, 0, "tank"] }, // [rT,rB,h, cx,cy,cz, mat]
  { "at": [-4.5,0,0.6], "repeat": 4, "step": [3,0,0], "items": [   // группа с повтором
      { "box": [0.95,0.9,0.85,  0,0.85,-0.15, "pump"] },
      { "cyl": [0.34,1.3,  0,1.0,0.75, "pump", "z"] }
  ]}
]
```

Координаты — модельные метры; ось `cyl` — `x|y|z` (по умолчанию `y`); группы
(`at`/`repeat`/`step`/`items`) вкладываются. Имена материалов маппятся в системы
через `matRules`, как и у именованных генераторов; `hotParts`/`flows`/`markers`/
разборка — всё работает. Валидатор build.js проверяет форму каждого примитива.

Демо: **`Насосная станция ВНС (голограмма).html`** (`configs/vns.json`) —
водопроводная станция II подъёма (резервуары с коническими крышами, 4 насосных
агрегата, всасывающий/напорный коллекторы, гидроаккумуляторы, ЧРП) построена
**без единой строчки кода в движке**. Дробные координаты маркеров/потоков удобно
считать из модельных: bbox складывается из тех же extents примитивов —
см. **`engine/tools/gen-vns.js`**: геометрия и точки задаются в метрах, скрипт
сам считает bbox и пишет готовый `configs/vns.json`. Копируйте как шаблон для
новых объектов (`node tools/gen-vns.js`).

### Режим «учебный стенд» (нумерованные узлы + ТТХ)

Для единого меша (скан/TRELLIS), который нельзя разобрать на детали, узлы
обозначаются **нумерованными 3D-метками-выносками** — они задаются точками, а не
частями меша, поэтому работают на любой модели. Наведение/клик по номеру (на
модели или в списке) → название и описание узла. Справа — список узлов и таблица
характеристик из референса.

```jsonc
{
  "specs": {                                   // таблица ТТХ (правая панель)
    "title": "ОБЩИЕ ХАРАКТЕРИСТИКИ",
    "rows": [ ["Базовое шасси","КамАЗ-6520"], ["Объём цистерны, м³","12"] ]
  },
  "markers": [                                 // нумерованные узлы
    { "n":1, "name":"Цистерна", "desc":"…", "at":[0.5, 0.68, 0.6] }
  ],
  "calibrate": true                            // показать кнопку калибровки (по умолч. да)
}
```

**Координаты `at:[fx, fy, fz]` — доли габаритного бокса 0..1**: `fx` — ширина,
`fy` — высота (0 = низ, 1 = верх), `fz` — длина. У «Илососа» длина идёт по Z:
`fz=0` — кабина/перёд, `fz=1` — задняя часть.

**Калибровка точек.** В стенд-режиме есть кнопка «⊕ калибровка». Включите её и
кликните по нужному месту модели — внизу (и в консоли) появятся координаты
`at:[…]`, которые можно вставить в конфиг. Так точки доводятся за пару минут.
Для публичной версии калибровку можно скрыть: `"calibrate": false`.

## 5. Создание моделей по референсам (2D и 3D)

Это ключевой исследовательский вопрос. Выводы по факту разбора моделей в директории:

### A. Готовые 3D-модели (GLB/glTF)
- **Авторские/CAD-модели** (как `aAIgtiiP.glb`: 142 меша, 34 материала) — идеальный
  вход: богатая структура материалов даёт **полную разборку на системы**. Это
  верхний предел качества движка.
- **Источники**: библиотеки 3D-моделей (Sketchfab, CGTrader, TurboSquid), экспорт
  из CAD/BIM (Revit/IFC → glTF), Blender. Для ЖКХ-техники и оборудования —
  оптимальный путь, если модель имеет именованные материалы/узлы.
- Требования к модели для structured-режима: **осмысленные имена материалов или
  узлов** (по ним работает `matRules`). Если их нет — будет `whole`.

### B. 2D-референс → 3D (image-to-3D)
- В директории уже есть результат **TRELLIS** (`Trellis2_HighQuality_00001_.glb`) —
  это подтверждает рабочий пайплайн «одна картинка → 3D». Microsoft **TRELLIS**
  (и аналоги: **Tripo / TripoSR**, **Hunyuan3D-2**, **Stable Fast 3D**, **Meshy**,
  **Rodin**) генерируют GLB из 1–4 фото.
- **Реальность результата**: такие модели — **единый слитый меш без материалов и
  частей** (как `Илосос.glb`). Поэтому из 2D-референса сейчас получается
  **отличная цельная голограмма (`whole`)**, но **не** автоматическая разборка на
  узлы. Это объективное ограничение image-to-3D, а не движка.
- **Рекомендуемый конвейер по референсам**:
  1. фото объекта (желательно ¾-ракурс, чистый фон) →
  2. image-to-3D (TRELLIS/Tripo/Hunyuan3D) → GLB →
  3. (опц.) чистка/ретопология в Blender, разнесение по материалам если нужна разборка →
  4. `build.js` → готовая голограмма.

### C. Очистка «помятого» вида сканов (реализовано)
Сырой меш TRELLIS/фотограмметрии шумный и часто несваренный → `EdgesGeometry`
рисует почти каждое ребро треугольника, и каркас выглядит мятым. В whole-режиме
движок **автоматически** чистит геометрию перед извлечением рёбер:
1. **сварка вершин** по координате → настоящая смежность граней;
2. **лапласово сглаживание** (`smooth` итераций) → снимает поверхностный шум;
3. **более грубый угол рёбер** (whole-карта плотности 20–48° против 3–18°) →
   остаются только структурные складки.

Эффект на «Илососе»: рёбер каркаса **1 257 856 → 279 346** (×4.5), форма сохранена,
«помятость» убрана. Тонкая настройка — `smooth` / `smoothLambda` / `weldPrecision`
в конфиге и кнопки плотности каркаса в самом вьювере.

**Чёткий контур по рёбрам** (`outline`) — главный приём для скан-моделей.
`EdgesGeometry` поверх шумного TRELLIS-меша либо спеклит, либо рвёт линии. Вместо
этого оболочка рендерится в offscreen-буфер, куда пишутся **нормаль (rgb) и
глубина (a)**; затем экранный пасс рисует линию там, где **ломается нормаль**
(`contourNormal`) или **прыгает глубина** (`contourDepth`). Это даёт за один проход
и внешний силуэт, и внутренние рёбра (кабина/цистерна/колёса), с порогом, который
**отсекает поверхностный шум** скана. Линия вид-стабильна при любой плотности меша.

В whole-режиме шумный 3D-каркас почти выключен (`contour`≈0), внутри остаётся лишь
очень слабый «призрак» (`fill`≈0.15) для голографического объёма, а чёткие линии
даёт экранный контур. На structured-модели (Суперкар) экранный контур по умолчанию
выключен — там работает эталонный 3D-каркас.

Эффект на «Илососе»: вместо «помятой фольги» — чистый непрерывный контур
(силуэт + кабина + колёса + цистерна + манипулятор) без спекл-шума.

### D. Чтобы получить разборку для AI/скан-моделей
Три пути «добавить части» единому мешу:
1. **Геометрическая авто-сегментация** — **✅ реализовано:** `tools/blender-prep.py`
   (нужен Blender, headless). Один проход: сварка → vertex-smooth → **planar-децимация**
   (`dissolve_limited`: копланарные треугольники схлопываются в фасеты — рёбра между
   фасетами становятся чёткими «как у CAD», скан перестаёт шуметь в EdgesGeometry) →
   раздача **материалов по зонам** центроидов фейсов (без разрезания геометрии).
   Зона: `{name, tmin/tmax (доля вдоль длинной оси), zmin/zmax (доля высоты)}`,
   первая подходящая выигрывает, без условий = default. Движок дальше делит на
   системы обычным `matRules` → подсветка/выбор/разборка работают из коробки.
   ```bash
   # оси/габариты/профиль высоты (куда класть зоны):
   blender --background --python tools/blender-inspect.py -- ../scan.glb
   # чистка + фасетизация + зоны (296k→158k граней на мусоровозе):
   blender --background --python tools/blender-prep.py -- \
     --in ../scan.glb --out ../scan-parts.glb --weld 0.0002 --smooth 2 --angle 4 \
     --zones '[{"name":"hodovaya","zmax":0.22},{"name":"kabina","tmax":0.28},
               {"name":"bunker","tmin":0.82},{"name":"kuzov"}]'
   ```
   В конфиге поставьте `smooth: 0` (уже сглажено; наш Лапласиан разрушит фасеты).
   Проверено: Мусоровоз (Seedream→TRELLIS-скан) → 4 системы, select/explode/hot
   работают — `configs/musorovoz-parts.json`, «Мусоровоз разборный (голограмма).html».
2. **Ручной редактор зон**: бокс-выделение и тегирование частей → точный конфиг
   `parts`/назначения. Точно, но трудозатратно на каждый объект. _(не реализовано;
   частично закрывается подбором зон через blender-inspect + калибровку)_
3. **Многокомпонентная генерация**: собирать объект из отдельных деталей (каждая —
   своя AI-модель/материал), тогда `structured` работает «из коробки». **✅ реализовано:**
   режим `build.js --parts <dir>` — папка `*.glb` (по файлу на узел), каждый файл
   тегируется ключом `partNN` и становится системой; `mode/parts/matRules` авто-заполняются.

**Part-aware генерация** (из одной картинки сразу несколько частей):
`ComfyUI_PartPacker` (нода ComfyUI, ≤12 ГБ VRAM), **PartCrafter** (NeurIPS 2025, есть
demo на HuggingFace), **OmniPart** (SIGGRAPH Asia 2025). Дают геометрические части
(«верх/низ»), не инженерные системы, и на технике ЖКХ качество надо проверять.
Скелет пайплайна ComfyUI→голограмма (MCP-триггер + `--parts`) — в [`comfyui/README.md`](comfyui/README.md).

## 6.5. Картинка и камера

- **Финальный пасс ACES tone-map + цветокоррекция** (`grade`): добавлен `ShaderPass`
  после bloom — мягко «скручивает» пересветы (яркие ядра больше не выгорают в белый),
  плюс лёгкая прохладная цветокоррекция под голографический синий. Ручки:
  `grade.exposure / contrast / saturation`.
- **Кинематографичные переходы камеры**: fov/азимут/наклон/дистанция/цель плавно
  доезжают до цели (включая зум fov 42↔10 для «Плана этажа»). «План этажа» —
  near-ortho сверху под 86° (без gimbal/крена). Авто-вращение отключено в режимах
  плана и разреза.
- **Живая настройка вида — кнопка «⚙ Вид»**: панель с ползунками (контур внешний /
  контур внутренний / **детализация нутра** / заливка каркаса / оболочка /
  свечение-bloom) меняет картинку мгновенно, без пересборки. Кнопка «⧉ в конфиг»
  копирует текущие значения JSON-сниппетом — подобрал вид глазами → вставил в
  `configs/*.json`.
- **Вращение — по кнопке «↻ Вращение»** (по умолчанию выключено): авто-облёт
  включается вручную, а не сам через простой.
- **Реакция на курсор**: при наведении мыши модель мягко доворачивается за
  курсором (параллакс) и контуры чуть ярче — голограмма «живёт» под мышкой.
- **Двухцветные контуры**: силуэт голубой, внутренние переломы — янтарные
  (`outlineInnerColor`), устройство визуально отделяется от оболочки.

> Приёмы навеяны OSS-набором `threejs-awesome-graphics-agent-skills` (MIT), но
> перенесены вручную: сам пакет рассчитан на современный Three (модули/TSL/WebGPU) и
> фотореализм, а наш рантайм — Three r134 (глобальный THREE) + проволочная голограмма,
> поэтому ядро осталось нашим.

## 6.6. Анимация потоков среды — `flows`

Показывает, **как работает объект**: по контурам бегут светящиеся стрелки вдоль
направляющих труб (теплоноситель, пар, газ, ГВС, ХВС…). Управляется массивом
`flows` в конфиге — работает в любом режиме (GLB или процедурный):

```jsonc
"flows": [
  {
    "kind": "Тепловая сеть (первичный)",   // подпись в легенде
    "color": [1.0, 0.32, 0.12],            // цвет стрелок (или по kind: heat/secondary/cold)
    "speed": 0.07,                         // доля пути в секунду
    "count": 7,                            // число стрелок (по умолчанию из длины пути)
    "at": [ [fx,fy,fz], … ]                // ломаная в ДОЛЯХ bbox (как у markers.at)
  }
]
```

Точки `at` — те же дробные координаты bbox, что у выносок (`markerNorm`), поэтому их
удобно снимать через режим **калибровки**. По точкам строится `CatmullRomCurve3`,
вдоль неё — слабая направляющая труба (`TubeGeometry`) и `count` конусов-стрелок,
ориентированных по касательной; всё аддитивно светится и попадает в bloom. Замкнёте
ломаную (последняя точка ≈ первой) — получится непрерывный контур (подача→обратка).

Кнопка **«⇢ Потоки»** включает/выключает анимацию, снизу-слева — **легенда цветов**.
Потоки автоматически прячутся в режимах «Разобрать», «План этажа» и «Разрез фасада».
Реализация: `buildFlows` / `buildFlowLegend` / `updateFlows` / `toggleFlow`,
`state.flow`. Настроено в трёх объектах ЖКХ:
- `configs/ctp.json` — сеть (первичный) / отопление+ГВС (вторичный) / ХВС;
- `configs/boiler.json` — теплоноситель / газ / дымовые газы;
- `configs/power.json` — пар и конденсат / электроэнергия / охлаждение (градирни).

## 6.7. Голо-рой (частицы) — `particles`

Живое облако из десятков тысяч частиц по поверхности модели — эффект
«материализации из пыли» (по мотивам casberry AI Particle Simulator: позиция
каждой частицы = функция цели, времени и seed). Работает в любом режиме —
GLB-скан или процедурное здание:

```jsonc
"particles": {
  "on": true,          // рой включён при загрузке (кнопка «✦ Рой» есть всегда)
  "count": 40000,      // частиц (1000..120000, по умолчанию 45000)
  "intensity": 0.55,   // общая яркость (0..2; для сцен с bloom.threshold 0 — ниже)
  "size": 34,          // базовый размер точки, px (по умолчанию 40)
  "swirl": 0.42,       // curl-дрейф вдоль поверхности (0..1)
  "breath": 0.35       // «дыхание» по нормали (0..1)
}
```
`"particles": false` полностью убирает кнопку и ползунки.

Цели сэмплируются равномерно по площади треугольников `meshData` (бинарный поиск
по накопленной площади), поэтому рой автоматически наследует разбивку на системы:
`aPart`/`aHot` — «горячие» части (`hotParts`) светятся янтарным (`uColor2`) и
крупнее, выбор системы подсвечивает её частицы белым и гасит остальные, разборка
(`aExplode`) разносит частицы вместе с их системами, план этажа и разрез фасада
режут рой теми же uniforms, что и основные пассы. Сборка при загрузке — из
сферического разлёта (общий `uProgress`).

Ползунки «Рой: яркость/кружение/дыхание» — в панели «⚙ Вид», «⧉ в конфиг»
экспортирует их как плоские ключи (`particlesIntensity` …) — движок читает и
плоскую, и вложенную форму. Реализация: `36-particles.js`
(`buildParticles` / `toggleSwarm` / `ensureSwarmU`, `state.swarm`); геометрия
строится лениво при первом включении и переживает пересборку рёбер (смену
плотности). Включено по умолчанию в `configs/mkd.json`.

## 7. Технические детали оффлайн-бандла

Выходной HTML — самораспаковывающийся:
1. `__bundler/manifest` — все ассеты (Three.js, аддоны, Draco-wasm, шрифты, модель)
   в base64, бинарные — ещё и gzip.
2. `__bundler/ext_resources` — карта `id → asset` (`objModel`, `dracoWasm`, …).
3. `__bundler/template` — HTML вьювера в виде JSON-строки; `</` закодированы как
   `/`, чтобы внутренний `<script>` не закрыл тег раньше времени.

При открытии скрипт-распаковщик декодирует ассеты в blob-URL, подставляет их в
шаблон и монтирует вьювер. Поэтому файл работает и по `file://`, и на сайте.

Размер: ~14–16 МБ на объект (определяется размером GLB). Для уменьшения —
Draco/Meshopt-сжатие модели перед сборкой (будущая опция пайплайна).
